# DevSecOps ticket automation at 1,000-person scale: false-closure counter-test OODA cycle — 2026-09-06 10:36

**Focus area:** Counter-test the proposed control architecture against false resolution, weak validation, model overconfidence, and unsafe promotion to automatic action.
**Research mode:** Counter-evidence deep-dive plus current evaluation practice.
**Why this focus:** A large software unit can produce a clean audit trail for the wrong state transition. This round asks what “resolved” must mean and how an action class earns more autonomy.

## Findings

### A detector-state transition can manufacture a false security resolution

**Source:** https://gitlab.com/gitlab-org/gitlab/-/work_items/620336 — [practitioner direct]
**Date:** observed 2026-08-22; fetched 2026-09-06
**Agent level:** Team → company
**What:** A reproducible GitLab.com case enabled Advanced SAST on an unchanged WebGoat commit. Of an approximately 94-finding Semgrep baseline, 23 records were converted to the new analyzer and the remaining 71 were auto-resolved as “no longer detected”; one was a critical SSRF finding. No code changed. The work item proposes scanner-aware handoff or a separate re-triage outcome instead of resolution.
**Evidence level:** L2 single reproducible incident record, not cross-company convergence.
**Key claims:** Detector disappearance is not remediation evidence. Analyzer identity and version, commit SHA, finding identity, and the reason for disappearance must travel with closure.

### Current autofix validation is useful but explicitly incomplete

**Sources:** https://docs.github.com/en/code-security/concepts/code-scanning/autofix-for-code-scanning — [vendor documentation]; https://docs.github.com/en/code-security/responsible-use/security-and-quality-ai-features — [vendor documentation]; https://dev.to/pwd9000/can-copilot-fix-its-own-security-findings-testing-github-agentic-autofix-351b — [practitioner direct]
**Dates:** live GitHub documentation checked 2026-09-06; Marcel Lupo, 2026-08-17
**Agent level:** Team
**What:** GitHub labels agentic autofix a public preview and says its validation is best-effort: its built-in CodeQL rerun cannot confirm custom or security-extended queries, and third-party fix quality is not guaranteed. GitHub's internal harness uses more than 2,300 public-repository alerts with test coverage, reruns scanning and tests, uses multiple runs for nondeterminism, and spot-checks successful suggestions—but still instructs developers to review intended behaviour. Lupo turns those limits into a reproducible sandbox evaluation and explicitly avoids claiming an unrun success.
**Evidence level:** L0 vendor evaluation and capability disclosure plus L1 practitioner evaluation method.
**Key claims:** The originating scanner's actual PR workflow must re-prove closure; a clean result from a different scanner is not equivalent evidence. Functional, contract, and negative-security tests remain a separate postcondition.

### Organizational metrics must measure the routed-out cases, not only accepted fixes

**Sources:** https://docs.github.com/en/code-security/concepts/code-scanning/pull-request-alert-metrics — [vendor documentation]; https://snyk.io/blog/remediation-agents-demystified/ — [vendor press release]
**Dates:** live GitHub documentation checked 2026-09-06; Snyk Team on Gérald Crescione, Ryan McMorrow, and Brendan Hann, 2026-08-19
**Agent level:** Company
**What:** GitHub exposes alert outcomes including fixed with or without Autofix, unresolved-and-merged, false-positive dismissals, risk acceptance, remediation rate, and time to remediate. Snyk's own account says naive patches were often rejected and its current workflow stops at a PR, rescans, and runs project tests. Neither source publishes a calibrated organization-wide probability of safe action.
**Evidence level:** L0 capability and vendor report.
**Key claims:** Agreement and merge rate are insufficient. A large-unit pilot also needs sampled false negatives, reopen rate, reverts/rollbacks, escaped incidents, human overrides, evidence completeness, and results by action class.

## Safe Promotion Ladder

1. **Shadow:** classify and draft evidence without touching ticket state.
2. **Suggest:** write proposed routing, disposition, and candidate rule for a human.
3. **Prepare:** open a PR or a non-executed runbook plan; never merge or run.
4. **Canary:** automatically execute one pre-approved, reversible action on one bounded target; read back the post-state; stop on the first failure.
5. **Narrow automatic:** expand only that action class after stable measured results; keep sampling abstentions and closures; demote on model, scanner, rule, repository, or runbook change.

Promotion is per action class, not per agent. “Update labels” may be automatic while “dismiss critical alert,” “merge dependency upgrade,” and “disable IAM principal” remain three different authorities.

## Required Ticket State Machine

`observed → enriched → validated → routed → proposed → verified → approved-if-required → executed → post-state-observed → closed`

`contained`, `accepted risk`, `duplicate`, `false positive`, and `analyzer handoff` are distinct terminal or holding states. `Resolved` is computed from independent evidence; it is not free text the same agent may award itself.

## What I Looked For But Did Not Find

No independent 10–20-company convergence supports closed-loop agent handling from GitHub/AWS finding to verified resolution. No public 1,000-person unit reports the false-negative rate of automatic triage or the harmful-action rate of automatic remediation. No published calibration transfers across repositories, scanners, model versions, and AWS accounts. I found no defensible path to “absolute correctness” for semantic intent—only hard guarantees for declared permissions, predicates, and observable postconditions.

## Orientation

**Automate the evidence chain, not the authority chain.** The largest demonstrated failure in this sweep was not a wild agent action; it was a plausible, policy-driven status change that silently converted “not reported by this analyzer” into “fixed.” Safe automation must make those states impossible to conflate.
