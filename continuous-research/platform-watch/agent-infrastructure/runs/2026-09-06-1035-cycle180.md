# DevSecOps ticket automation at 1,000-person scale: action authority OODA cycle — 2026-09-06 10:35

**Focus area:** The smallest enforceable control architecture for moving from a DevSecOps ticket to a GitHub or AWS action without giving one agent broad administrative authority.
**Research mode:** Cross-platform capability deep-dive and architecture composition.
**Why this focus:** Cycle 179 separated central policy from local intent. This round asks which presently shipped controls can enforce that separation at execution time.

## Findings

### GitHub can make an agent's output reviewable without making the agent a merger or deployer

**Sources:** https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets — [vendor documentation]; https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments — [vendor documentation]; https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws — [vendor documentation]; https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-with-reusable-workflows — [vendor documentation]
**Dates:** live documentation checked 2026-09-06
**Agent level:** Team → company
**What:** Rulesets can require a pull request, named status checks, code-owner review, review by someone other than the last pusher, and restrictions on bypass. Protected environments can require a reviewer, prevent self-review, and restrict deployment branches. GitHub OIDC replaces long-lived AWS secrets with short-lived credentials whose trust policy can bind the repository, branch, environment, or centrally maintained reusable workflow.
**Evidence level:** L0 capability evidence.
**Key claims:** A patch agent can be confined to a bot branch; an independent checker can own required status; a human or policy gate can own merge; and only a protected deployment workflow can request a narrowly scoped AWS role.

### AWS exposes approval, postcondition, and blast-radius controls as runbook primitives

**Sources:** https://docs.aws.amazon.com/securityhub/latest/userguide/securityhub-v2-eventbridge-automations.html — [vendor documentation]; https://docs.aws.amazon.com/systems-manager/latest/userguide/automation-action-approve.html — [vendor documentation]; https://docs.aws.amazon.com/systems-manager/latest/userguide/automation-actions.html — [vendor documentation]; https://docs.aws.amazon.com/us_en/systems-manager/latest/userguide/running-automations-scale-controls.html — [vendor documentation]
**Dates:** live documentation checked 2026-09-06
**Agent level:** Company
**What:** Security Hub can route findings through EventBridge into tickets, Lambda, Step Functions, or Systems Manager. Systems Manager runbooks can pause for authenticated approval, abort on failure, branch, wait for resource state, and assert resource properties. At fleet scale, concurrency and error thresholds bound how many targets run simultaneously and stop new work after failures.
**Evidence level:** L0 capability evidence.
**Key claims:** High-risk actions need not rely on the agent remembering a safety instruction. Approval, target constraints, failure behaviour, and post-state checks can live in the execution substrate.

### Containment and resolution must remain different states

**Sources:** https://docs.aws.amazon.com/solutions/latest/automated-security-response-on-aws/multi-service-remediation.html — [vendor documentation]; https://docs.aws.amazon.com/solutions/latest/automated-security-response-on-aws/adding-new-remediations.html — [vendor documentation]
**Dates:** live documentation checked 2026-09-06
**Agent level:** Company
**What:** AWS's current Automated Security Response design explicitly describes GuardDuty and Macie remediations as first-line containment that leaves the underlying finding visible for manual follow-up. It also warns that immediate automatic remediation needs careful risk consideration and requires each remediation to use a properly scoped role with only the necessary API calls.
**Evidence level:** L0 capability evidence.
**Key claims:** Disabling a key or blocking public S3 access may reduce exposure without resolving the incident. The workflow must represent `contained` separately from `resolved`, or fast automation will create false closure.

## Minimum Separation of Duties

| Identity | May do | Must not do |
|---|---|---|
| Observer / triage agent | Read findings and context; enrich, deduplicate, route, propose | Mutate repositories or cloud resources; close from its own judgment |
| Patch agent | Write a bot branch; open or update a pull request | Push to protected branch; approve; merge; deploy |
| Verification identity | Run the authoritative scanner, tests, and postcondition reads | Change the candidate; grant its own check |
| Merge / deployment gate | Apply deterministic rules and collect required approvals | Generate the candidate it judges |
| AWS remediation role | Run one versioned runbook against an explicit resource class | Hold broad account administration; choose new operations dynamically |

**Invariant:** no component may both decide that an action is eligible and execute it with the same identity.

## What I Looked For But Did Not Find

No GitHub or AWS control creates an atomic transaction across a ticket, a repository, and live cloud state. Duplicate events, delayed scans, retries, analyzer changes, and partial execution remain application-level concerns. I found no independent production study measuring whether this five-identity split reduces harmful agent actions, and no public calibration showing which AWS remediations are safe to promote from approval-required to automatic across heterogeneous accounts.

## Orientation

Action governance is no longer “completely unbuilt”; its enforcement primitives exist. What remains missing is the composed, independently validated cross-system governor. For M10, the lesson is to wire those primitives into a narrow state machine—not to deploy an omnipotent ticket bot.
