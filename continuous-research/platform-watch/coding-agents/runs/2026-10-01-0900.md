### Finding 2: HydraFusion — Context Architecture Limitation Documented by Independent Technical Analysis

**Source:** [memorylake.ai/en/blogs/copilot-hydrafusion-per-request-context](https://www.memorylake.ai/en/blogs/copilot-hydrafusion-per-request-context) — [practitioner analysis]
**Date:** 2026 (exact date not confirmed)
**Agent level:** personal / team
**What:** Independent technical analysis identifies a structural architectural gap: HydraFusion's per-request routing means **no single model in the execution chain retains project context across requests**. The author distinguishes two types of context: (1) *invariant knowledge* (build commands, style guides) — belongs in instruction files, survives routing; (2) *discovered knowledge* (why certain decisions were made, constraints learned through correction) — cannot survive within any single routed model. The framing: "whatever your agent needs to know tomorrow has to be written somewhere that survives the routing decision, because the routing decision is no longer yours to make." Solution: externalize all discovered context to memory infrastructure that all workflow legs can access, explicitly. This is not unique to HydraFusion — it extends the existing analysis of per-request routing → context discontinuity (Cycle 224 MemoryLake L4 cross-vendor meta-pattern finding), now with the explicit invariant/discovered taxonomy.
**Evidence level:** Level 2 (single analyst characterization; independent of GitHub/vendor; consistent with Cycle 224's broader pattern finding)
**Key claims:**
- Invariant knowledge survives routing; discovered knowledge does not
- Teams relying on models to "remember" project context will encounter silent failures
- Mitigation: explicit memory externalization required for production agentic workflows on HydraFusion
- Finding extends the L4 meta-pattern from Cycle 224 (HydraFusion + Amp = per-request routing → context discontinuity) with a practical taxonomy
